The fastest code I wrote last week was the code I didn't write

I made an AI model generate text 1.72× faster. The optimisation everyone told me to build next would have gained under 6% — and I only knew that because I did the arithmetic before writing it.

—The kitchen

A chef, a waiter, and six thousand slips of paper

Picture a kitchen. The chef is extraordinary: chops, sears and plates faster than you can follow. Beside the chef stands a waiter whose only job is handing over instruction slips. Chop the onion. Now the garlic. Now stir.

One dish takes six thousand slips. The waiter needs about three milliseconds per slip. The chef needs roughly fifteen seconds of actual cooking. The dish takes thirty-three seconds to leave the kitchen.

The chef spends more than half of service standing still, holding a knife, waiting for a piece of paper.

Everyone who walks into that kitchen says the same thing: you need a faster chef. Sharper knives. A hotter stove. I measured the chef. The chef was already working at 87% of what physics allows.

The fix was to hand over the entire recipe on one page, once, and never speak again.

The chef is a graphics card. The waiter is the main processor. The dish is one word of text coming out of an AI model. Everything below is that story with the numbers attached.

0.83×Act one
It got slower

I did the obvious thing and the system got worse

Language models spend more effort moving numbers around than doing arithmetic on them. The standard remedy is fusion: instead of five small operations that each read from memory and write back, write one operation that does all five in a single pass.

I wrote two fused operations, twice each — once for NVIDIA cards, once as hand-written kernels for Apple silicon, so I could compare two very different machines. In isolation they were fast.

5.7×fused normalisation, best case
229 GB/s95% of the memory system's real limit
0.83×the same code, whole model

The profiler explained it in about thirty seconds. Matrix multiplication was 76% of the card's time. Everything my fused code touched added up to 19%. A flawless fusion had a 19% ceiling, and mine cost more than it saved.

Here is the specific embarrassment. Generating text produces one word at a time, and each step processes a single row of numbers. My kernel was 5.7× faster on two thousand rows and 0.42× on one row — less than half the speed of the code it replaced. Starting a custom kernel has a fixed cost, and at one row that cost exceeded everything the fusion saved.

The fix was small: below a threshold, don't use the fused version. But I refused to guess the threshold. I measured it — fusion loses at 8 rows and wins at 32 — and the code now re-measures it on whatever machine it lands on.

A 5.7× speedup on 19% of the work is exactly that. The number that decides anything is the one at the end.
<6%Act two
Never written

The kernel I didn't write

With the regression fixed, the next target looked obvious. Matrix multiplication was 76% of the time. Everyone optimises matrix multiplication; there are famous blog posts about it.

Before writing a line, I did the arithmetic. To generate a single word, a model must read every weight it has out of memory. For this model that is 3.09 GB, per word. That card's memory delivers 241 GB/s, measured on the machine rather than taken from a datasheet.

NVIDIA's existing code was running at 87% of the physical wall. A flawless hand-written replacement — better than a library tuned for a decade — was worth 1.8 milliseconds of a 32 millisecond word.

I didn't write it. That decision sits in the repository with the numbers that justify it.

The expensive thing in engineering is not slow code. It is a week spent speeding up something that was never the reason things were slow.
1.72×Act three
The actual fix

The bottleneck nobody was looking at

If the arithmetic takes 14.6 ms and the word takes 32.0 ms, something is consuming 17.4 milliseconds doing nothing visible.

The card was idle. Every operation a model performs must be dispatched — the processor telling the card what to do next. Each instruction is cheap, about 2.84 microseconds. Generating one word takes 6,130 of them.

6,130instructions issued per word
2.84 µscost of issuing one
54%of every word, card idle

No kernel fixes this. You could make the card infinitely fast and the processor would still need 17.4 ms to describe the work.

The fix is a recording. Instead of issuing six thousand instructions per word forever, you record the sequence once and replay it. One submission instead of six thousand.

28.0words/sec before
48.1words/sec after
1.72×more than every kernel combined
86%The prediction

It was called in advance, in milliseconds

Before any of the recording code existed, the analysis said the wasted time was 17.4 milliseconds per word. When it worked, the recording had recovered 14.9 milliseconds.

86% of a number predicted in advance, in real units, before the code was written. The same arithmetic that predicted this is what told me not to write the matrix multiplication kernel. One afternoon of it saved a week and pointed at the thing that actually worked.

One detail I want to be precise about, because it is how projects like this quietly go wrong. A recording that replays against the wrong memory does not crash. It produces text that is completely fluent and completely wrong, and nothing raises an error anywhere. So the benchmark refuses to print a speed number until the recorded version has produced word-for-word identical output to the original. This kind of generation is deterministic; identical is the only acceptable answer, not "close".

×2Also cancelled

Two more things I measured and then didn't build

Recording the prompt stage too — worth 1.006×

It sounds obviously worthwhile, and the reason it isn't is elegant. The instruction cost is fixed — 6,130 of them regardless of prompt length — while the actual work grows with the prompt.

On a short prompt the overhead is 40% of that stage, but the stage is 3% of the request. On a long prompt the stage dominates the request, but the overhead has shrunk to 1% of it. Squeezed from both ends, at every size from 128 to 8,192 words.

FlashAttention — worth 1.1%

The famous optimisation everyone reaches for. In this workload, attention was 1.1% of the card's time. Perfect attention would have been invisible.

Neither of these is a criticism of the technique. They are statements about this workload, which is the only kind of statement a measurement can make.

7×The instrument

What surprised me most: the ruler was broken

For three runs I could not prove the fused kernels helped end to end. The effect was around 5%, and my statistics kept answering "not resolved, take more samples". So I took more. Sixteen. Still nothing. It suggested twenty-one.

Then I ran the identical benchmark on a different free platform. Same code, same model, same class of card.

3.68measurement noise, platform A
0.53measurement noise, platform B
t = 9.8resolved immediately

The first platform's shared machine was bimodal: identical code clustered around two different speeds depending on what else was running on that host. You cannot average your way out of a broken instrument. More samples of a wobbling ruler give you a very precise measurement of the wobble.

When a test keeps failing and keeps asking for more data, suspect the instrument before the data.
—The point

Fast code is not the hard part

I could have shipped the 5.7×. It is true, it is measured, and it would have looked excellent on a slide. It would also have been useless, because the system it lived in got slower.

The three findings I would actually defend in a room full of engineers are these. The optimisation I built made things worse, and I published that. The optimisation I was told to build next was worth under 6%, and I calculated that before spending the week. And the thing that actually worked was invisible until I stopped looking at the graphics card and started looking at what was keeping it idle.

Knowing which code is worth making fast is the hard part.
